# 画面与声音

[适配流程](README.md) | [文档目录](../README.md)

固定逻辑频率，画面跟随显示器刷新。声音事件按真实游戏事件输出。

## 准备

准备一台 60 Hz 设备和一台高刷新率设备。使用固定输入或 Replay 比较游戏状态，再观察角色、弹幕、激光、特效、背景、菜单与暂停画面。

[Presentation Lab](../../common/testkit/presentation-lab/README.md) 用于重复绘制与状态对照；本作具备其他同等检查工具时，在表中记录对应入口。

## 人工显示审查表

机器先用同一构建和输入准备场景素材、帧范围和自动结果，人集中查看下列两个场景部分，整组选择一次“通过／发现问题／素材不足”。通过时工具关联整组素材；发现问题时补充对象、时间与现象。逻辑步进、状态纯度、对象身份和首帧时序由机器检查。

每个场景选定本作的独立参考：原版同输入录像、已确认的逐帧片段或明确的行为规则，来源写入记录的“预期依据”。暂停菜单中哪些元素应更新、贴图何时切换、瞬移发生在哪个边界，都写到具体对象和帧范围。

| 场景部分与关联编号 | 人工集中查看 | 应看到的现象 | 机器先准备 |
| --- | --- | --- | --- |
| 连续运动与限帧 \| DISPLAY-02／04／08 | 在实际高刷显示器比较限帧开关，集中查看角色、弹幕、激光、附属物、特效、背景和菜单的运动窗口 | 连续运动平滑，离散贴图切换自然；标出抖动、拖影和停顿 | 两种配置的提交记录、同输入逻辑对照、对象身份、连续端点和代表性图像／片段 |
| 边界与暂停 \| DISPLAY-04／05／06 | 集中查看出生、销毁、瞬移、切面、池复用和暂停／恢复片段，异常处再逐帧查看 | 新对象从当前状态出现，销毁后消失，瞬移无旧代拖线；世界与菜单的视觉表现符合本作设计 | 各事件的对象代次、有效状态、提交列表、真实暂停状态与对应边界图像／片段 |

视觉结果按对象、事件与场景保存。一个移动对象的窗口对应这一对象和窗口，出生与销毁等边界各有独立证据。工作台的强制 alpha 绘制用于比较插值结果；原生循环提交记录用于检查运行路径；显示器实际观感由现场审查记录。

th08 工作台将多个已导出的窗口加入一组素材，集中选择一次视觉结论，通过时无需逐编号写观察文字。工具逐份保存原始报告的字节数、SHA-256、Runtime、工具、DATA、Replay、场景和逻辑帧身份；整组素材对应同一构建与输入。审查者和设备信息在本次会话复用，刷新率按系统当前设置填写。加入、删除或替换素材后重新选择结论。人工记录覆盖实际查看的素材集，[验证记录](record-template.md#显示人工记录)与自动结果共同汇总验收范围。

## 可审查的验收方法

以下方法供逐项审查，当前入口说明实际覆盖范围。

### DISPLAY-01 | 固定逻辑步进

- 场景与操作：在 60 Hz 与更高刷新率设备加载同一模式、DATA 和固定输入／Replay，按相同逻辑边界采样。
- 权威观察与预期：读取本作逻辑帧、RNG、计时和 Replay 位置，并与同输入参考逐边界比对；刷新率只改变呈现机会。
- 通过／失败：相同输入序列到达相同逻辑状态与 Replay 边界即通过；逻辑时钟随额外绘制次数变化即失败。
- 反例：让模拟更新错误地绑定每次绘制，确认逻辑帧或状态摘要立即偏离。
- 当前入口与覆盖：各作 `frame-scheduler`／presentation 单测覆盖组件逻辑，th15 有 `tests/sdl/high-refresh-browser.test.mjs`；跨设备同输入对照仍按实测设备记录。
- th08 normal Lab 的生产帧回调经 `LabController.frameAt(timestamp)` 转发给 `Th08RuntimeDriver`，再调用诊断 ABI `sdl_presentation_audit_frame_at_v1`。原生时序环按 `base/capacity/count/next/stride` 读取；每个受控回调必须让 `next` 前进一格并按容量更新 `count`，报告同时保留回调结果与前后游标。

### DISPLAY-02 | 跟随显示器刷新率

- 场景与操作：在系统报告为 120／144 Hz 的显示器进入可操作关卡，持续移动角色并采集浏览器绘制与实际提交帧时间。
- 权威观察与预期：把浏览器／合成器的已呈现帧时间与设备当前刷新设置对照，同时读取原生逻辑帧；只以提交帧证据计呈现。
- 通过／失败：额外绘制机会跟随设备刷新而逻辑状态仍按本作时钟推进；只有 RAF 回调增加、画面未提交不能通过。
- 反例：注入绘制回调但不提交画面，确认报告不会把回调数写成实际呈现数。
- 当前入口与覆盖：th15 `high-refresh-browser.test.mjs` 驱动虚拟 RAF 与原生帧；其他作品的 `runtime-browser.mjs` 记录原生呈现计数，不替代实体高刷验证。

### DISPLAY-03 | 额外绘制无逻辑副作用

- 场景与操作：在同一逻辑帧保存世界、RNG、计时和存档状态摘要，重复请求绘制，再重新读取这些状态。
- 权威观察与预期：使用本作只读观察和固定快照比较绘制前后逻辑字段；相同逻辑输入的绘制结果另行比较。
- 通过／失败：额外绘制不改变逻辑状态、RNG、Replay 或存档字节；任何一项变化即失败。
- 反例：在绘制路径推进动画随机数或更新对象池，确认快照定位到首个改变字段。
- 当前入口与覆盖：`common/testkit/presentation-lab` 提供重复绘制对照；th07 `singleplayer-presentation-purity-test.py` 与各作 renderer 测试覆盖部分生产路径，逐作完整状态仍由本作入口补齐。
- th08 只读状态快照按17个源映射摘要组比较游戏世界、完整 `GameplaySession` 与历史、练习配置、Replay 消费和录制字节、键盘／控制器／触摸瞬态、用户移动缓冲、成功保存载荷、同步音频计数、host cadence 与绘制所有者状态。报告同时保存摘要组到源字段的映射，并按[Presentation Lab 共享权威域](../../common/testkit/presentation-lab/CONTRACT.md#权威域)校验十类责任。
- th08 自动入口由 source contract 与 Web `BrowserRuntime::present()` 方法组件组成：后者编译并执行生产方法体，核对 render-only/capture、提交失败和 LanguageTrace 分支。它提供方法级证据；Lab 的权威快照负责重复绘制状态对照。
- 音频纯度在每次同步 `drawOnly` 返回后立即读取 AudioAudit 计数，覆盖原生音频管理与 SDL 操作；负控在同一绘制调用里额外执行一次 `sdl_audio_pump()`。异步设备队列和声音输出不属于此状态快照。
- 动态对象按原生 birth／retire 事件和代次键关联。PlayerBomb 的固定对象池在逻辑更新边界对照活动位，ASCII文本在真实追加／清空处发布生命周期，分数与时间弹字在创建、槽位覆盖、到期和重置处发布代次。事件环边界与对象身份由 common 分析器检查；屏幕像素、遮挡和显示器刷新使用对应图像与设备记录。

### DISPLAY-04 | 连续视觉字段插值

- 场景与操作：用固定输入选取两个连续逻辑样本，在其间增加绘制采样，分别检查玩家、弹幕、激光、附属物和动画切换。
- 权威观察与预期：连续字段按本作明确的采样映射与逻辑前后值检查；贴图、状态、出生／销毁仍按离散逻辑边界检查。
- 通过／失败：中间呈现符合本作连续字段契约，离散变化只在相应逻辑状态生效；旧状态残留或状态提前切换即失败。
- 反例：把连续坐标改成只取整网格，或在对象复用后沿用旧插值端点，确认位置／对象身份断言失败。
- 当前入口与覆盖：th09 `renderer.test.mjs`、th11 `anm-renderer`／`player-rendering`、th15 `position-interpolation` 等覆盖各自字段；不得把单个 renderer 或共用模块结果写成全部对象通过。

### DISPLAY-05 | 出生、销毁和瞬移

共用证据检查器关联原生生命周期环的前后快照、真实场景切换和对象池复用窗口。作品在诊断适配器声明报告格式与状态槽位；同一对象旧代退出、新代从当前状态绘制，并与五帧审查素材绑定。机器结果与整组视觉结论分别保存。

运动窗口要求 alpha 图像呈现连续变化；静态标题和出生边界保存对应状态的图像。素材按场景职责判定，集中进入同一组人工审查。

- 场景与操作：用固定关卡样本触发对象出生、销毁、瞬移／切面及对象池复用，跨越各自逻辑边界连续采样。
- 权威观察与预期：记录对象身份／代次、有效状态、当前逻辑位置及提交的绘制对象；新对象的当前状态构成独立预期。
- 通过／失败：新对象从自身当前状态绘制，销毁对象不再出现，瞬移不沿旧对象轨迹补间；任一旧代状态残留即失败。
- 反例：强制池槽位复用但保留前一对象的位置或贴图，确认代次与画面对象不匹配。
- 当前入口与覆盖：th11 有 `player-lifecycle`、`item-rendering`，th15 有 `player-lifecycle`、`stage-resource-lifetime` 等测试；逐作登记实际触发的对象类型与样本范围。
- th08 normal Presentation Lab 在其运行实例中保存标题到游戏的真实切面，并在连续 241 个逻辑步内捕获同一 owner/object 的 retire→更高代次 birth。边界时保存新代当前对象报告与五帧素材；机器校验事件顺序、代次、身份标记和新代位置不沿用插值，人工组集中查看边界与暂停素材。

### DISPLAY-06 | 暂停画面的表现

- 场景与操作：进入可操作关卡后打开本作暂停菜单，连续采样世界、对象动画及菜单呈现，再按本作流程退出暂停。
- 权威观察与预期：以原生暂停状态和世界逻辑帧为世界权威；菜单动画／光标依本作暂停界面的状态机单独观察。
- 通过／失败：暂停期间世界保持暂停，菜单只按其设计更新；世界帧继续推进或菜单错误冻结即失败。
- 反例：使用 GameOver／Restart 遮罩冒充暂停状态，确认暂停断言要求真正的 Pause screen。
- 当前入口与覆盖：`tools/ports/runtime-browser.mjs` 有原生暂停／重开检查，th11／th15 各有 `pause-frame`、`pause-menu` 等单测；截图补充菜单外观，不能代替帧状态。

### DISPLAY-07 | 实际呈现后报告首帧

- 场景与操作：从冷启动开始记录启动事件、首个绘制提交和浏览器实际呈现证据，覆盖初次加载与刷新后恢复。
- 权威观察与预期：把 Runtime 的 `first-frame` 与对应页面及画布的首次实际呈现事件按同一次导航身份关联。
- 通过／失败：首帧事件发生在可验证的实际呈现之后；仅完成初始化或提交绘制命令而没有画面呈现即失败。
- 反例：推迟合成器提交或保持画布空白，确认事件不能因 Runtime 初始化完成而提前通过。
- 当前入口与覆盖：`runtime-browser.mjs --presentation-replay=绝对路径 --presentation-ticks=600` 保存正式包冷启动与刷新导航的 Chromium 合成帧 PNG、画布区域、帧交换时间和 Runtime 发送时钟。共用判定器重读 PNG，要求同一导航中非空白画布的实际交换早于 `first-frame` 发送；原生 Present 计数与产物、DATA 身份一并绑定。物理显示器的刷新与观感集中进入 Presentation Lab 人工审查组。

### DISPLAY-08 | 限制到 60 Hz

- 场景与操作：在高刷设备运行相同关卡与输入，分别关闭和打开 60 Hz 呈现限制，记录实际呈现、逻辑帧和输入效果。
- 权威观察与预期：比较本作原生逻辑帧／已消费输入与呈现事件；限制开关只约束呈现频率。
- 通过／失败：开启限制后画面按 60 Hz 口径呈现，而逻辑速度、输入规则和 Replay 结果不变。
- 反例：让限帧器跳过模拟步或累积输入，确认逻辑帧／Replay 对照失败。
- 当前入口与覆盖：th15 `high-refresh-browser.test.mjs` 检查受限与未受限绘制循环；其他作品需执行同一设备操作并附本次刷新设置和原生帧记录。

### AUDIO-01 | 正常 OGG 音乐

- 操作：选择本地或远端 OGG，进入标题再开始一局，并按本作表要求切换曲目。
- 观察与独立预期：采集实际 PCM 输出和加载的 OGG 身份，将曲目与固定资源清单或独立原版执行对照。
- 判定：每个要求场景输出对应曲目，错误曲目、持续静音或未解码都失败；不设置未有依据的幅值门槛。
- 反例：界面显示已选择 OGG，但 Runtime 没有读取轨道或 PCM 全零，应失败。
- 当前入口与覆盖：`tools/ports/music-browser.mjs` 用正式 Runtime `configure`／`launch`、产品目录 mount 和逐文件 SHA-256 清单，对比 `music=none` 与 OGG 输出。th08 normal 从标题开始同一局，核对原生标题曲名、实际资源与 Runtime PCM，并进入第一关核对原生曲目和对应 OGG 输入。第一关预期取自 `GameplayControl.cpp` 的 `stage_music[0] == 1`，不是驱动侧另造曲目表；原生游标继续由 AUDIO-03／04 场景核对。AUDIO-01 的完整曲目表与所有切曲、循环覆盖保持 `complete:false`。`--plan-only` 核对 Runtime、DATA 与逐条 OGG 路由身份，并保持 `incomplete`。th11 的 9-word 原生统计把 cue 映射到 `MusicCatalog.hpp`；th15 的 11-word 原生统计把 track index 与 `music/manifest.json` 对应，两个作品同时记录 Runtime 输出 PCM。th08／th10／th20 通过各自可用的原生观察绑定输出来源；TH20 记录正式 phase/UI 观察。OGG 路由按作品隔离。

音乐浏览器报告为页面、Console、HTTP／请求、原生协议和响应身份错误保存 mode 与实际操作阶段。曲目检查读取标题与游戏阶段的关联错误，暂停、前后台和重启各自读取生命周期阶段；全局报告保留全部错误并决定本次场景总结果。

MIDI 观察在同一次浏览器调用中复制原生计数、桥接事件、合成器发送与 PCM，逐字节按序核对同一窗口。重开按关闭时的事件与发送位置划分新会话，原生新实例计数从本次打开开始比较。OGG 停止窗口读取 `Module.SDL3.audioContext` 的 Runtime 混音器；MIDI 同时读取 `TinySynth.getAudioContext()` 的压缩器输出与 `TinySynth.out` 乐器源。两条 tap 保存确切 source node 身份，并在同一 AudioContext 时钟快照中采样。每个 PCM 窗口保存目标 context、tap、状态、音频时钟与采样率，并要求 context 全程 running 且时钟逐窗推进。关闭后，仍运行的 context 按实际采样率推进 4096 帧，再采集八个窗口。Launcher bridge 在每次 TinySynth `_note` 的同步调用内记录其专属 AudioContext 创建的振荡器与缓冲源，并关联 MIDI channel、note、velocity、start／stop 时间和 `ended` 事件。reset 先执行 TinySynth 原 reset，再立即停止仍排在未来的 owned source；同 context 的其他 source 不纳入。TinySynth reset 的实测回执记录活动 voice 清零；Launcher bridge 随后重建完整湿支路，替换卷积与增益节点，同时保留冲激响应、归一化设置和增益值。乐器源 tap 与最终混音 tap 同步检查完整八窗静音；最终混音的全零 PCM 是停止验收依据，源生命周期记录明确关闭时每个音符 source 的停止边界，节点替换记录说明支路身份。TinySynth 的实际图包含直达压缩器与卷积混响路径，下一条 MIDI 消息使用新湿支路与原音色资源。OGG 静音窗口与 MIDI 音源窗口缺少输出 tap、context 挂起或时钟停滞时记为 incomplete；已关闭的 context 使用身份匹配的生命周期回执记录零个 PCM 样本。

OGG 重启前的观测单独记录原生 playing／ready／paused 状态、当前曲目与输入 SHA、PCM 目标 tap、context 时钟和采样率、首个非零窗口及采集尝试数。采样只纳入预期曲目正在播放时的 PCM；有限采集结束仍未出现可归属的非零样本时，PCM 结果记为 incomplete，原生状态和曲目身份仍分别报告。

### AUDIO-02 | 无 BGM 模式

音效直接输出由[共享队列检查](../../tools/ports/sfx-queue-invariants.mjs)约束：执行生产 `WebSfx.hpp` 的 JavaScript 音频图，在已有 3072／6144 帧混合 PCM 时渲染已知音效，要求首个输出样本已经包含该音效。把播放排到队尾的反例必须产生延迟并被拒绝。`browser-shell` 集合与 CI 同用这个入口，并从产品目录与工作区映射核对普通版、MP 的音频消费者。独立检查逐项执行、汇总失败，报告分别保存组件输出、消费者源码接线和使用其他音频路径的产品。

同一入口运行[受控增益校准](../../tools/ports/presentation-gain-calibration.mjs)：在离线 AudioContext 开始渲染前，把四次同刻增益操作和声源安排到固定未来帧。独立预期逐点核对完整输出、左右声道、首帧及 AudioParam 的 float32 参数转换；一个 ULP 的改动也会失败。

正式包的精确时序通过 `--suite=audio-latency` 执行。th08 普通版的场景由[音频适配器](../../tests/adaptation/adapters/audio.mjs)锚定到生产音效表、成功上传的 buffer 和标题菜单；[共享判据](../../tools/ports/sfx-latency-contract.mjs)检查实际 PCM。

该组在无界面 Chromium 中运行正式包和真实 AudioContext／AudioWorklet，按原生时钟采样，适合进入自动队列。窗口前后台行为由专门的桌面生命周期场景验证，实体声音设备的延迟由设备会话记录。

原生记录在 `SDL_GetAudioStreamQueued` 前后读取同一 AudioContext 时钟，并保留两个时刻及对应帧。队尾因此表现为上下界：正向通过要求有效起音早于下界，live 负控排到上界；时钟缺失或顺序异常时记录不完整，不用固定时长容差代替边界测量。

AudioWorklet 的 `markerReceivedAtFrame` 记录标记消息被处理的渲染块，可早于原生逻辑事件；它只说明 PCM 历史从何时开始可检查。判据按 session、事件和 voice 身份关联真实 `startPlanFrame` 与原生事件，再用连续 PCM 历史确认起音，并扣除同一 source buffer 的前导静音后比较队尾。

音频探针在 iframe 页面脚本运行前注册键盘捕获观察器，会话开始时启用记录；原生键盘监听器仍按原顺序处理真实输入。

| 操作 | 预期与判定 | 报告中的实际观察 |
| --- | --- | --- |
| 无 BGM 启动，在标题主菜单按确认进入难度菜单 | 真实浏览器按键触发本作确认音；音效独立于已有混合 PCM 直接输出 | 输入、原生逻辑事件、成功上传、direct／fallback 路由、目标 voice 和 PCM 首个非零样本 |
| 将 PCM 首样本扣除同一 buffer 在同采样率、播放速率和起点下的原始前导静音 | 有效起音帧早于事件发生时已排队 PCM 的末端 | 同一 AudioContext 帧轴上的输入、事件、有效起音帧及队尾，附实际源 buffer 的独立渲染 |
| 在难度菜单再次确认进入角色菜单，将同一目标 voice 的实际起播改到测得队尾 | 同一判据必须检出该次延迟 | 实际修改的事件与起播时间、同一 Worklet 的 PCM、判据拒绝原因 |

这组场景绑定 th08 normal 的确认音。射击、击中、曲目分轨与其他作品按各自登记的音效场景汇总。显示器、扬声器与系统音频设备引入的物理延迟由现场记录另列。

- 操作：选择无 BGM，进入玩法并触发原表列出的射击、击中等音效。
- 观察与独立预期：分别采集音乐轨和音效输出通道/事件，参考同一场景启用 OGG 时的独立轨道身份。
- 判定：BGM 轨无输出而音效仍产生对应 PCM；“全静音”不能作为无 BGM 通过。
- 反例：音乐关掉后音效设备也被停止，应失败。
- 当前入口/边界：th06 [`SoundPlayer.cpp`](../../ports/th06/src/SoundPlayer.cpp) 的 `PlaySounds` 启动共用 [`WebSfx.hpp`](../../common/include/eagler/audio/WebSfx.hpp) 输出；桌面场景按本作 Runtime mount 读取同一 voice pool 与 SDL3 AudioContext。可信 KeyZ 前准备输出 tap 的有界连续 PCM 历史，按真实渲染帧留存；采集位于生产增益与声道合并之后，生产输出连接也进入观察。

成功的 `AudioBufferSourceNode.start` 按 `voice.node` 唯一归属记录 session、voice、源节点、merge、tap 与音频时钟。按键边沿与 start 使用同一会话顺序，原生玩家消费者确认实际创建射击后再松键。采集会话覆盖松键后的完整 PCM 窗口，采样结束后读取并关闭会话，失败时同样完成清理。同一 voice 的每次重触发和停止分别划分源节点区间，PCM 按该区间核对；同 tap 的重叠检查纳入全部会话节点，包括松键后的重触发。PCM 历史保存有界的渲染帧缺口区间，源区间外的缺口不影响其连续样本判定，交叠缺口或缺口索引溢出会标记证据不完整；零渲染帧会指出对应源节点、生产 tap 与帧边界，不会作为静音结论。

发送真实按键前，`armInputWindow` 通过已连接的共享 AudioWorklet 历史句柄观察各生产 tap 的真实渲染帧。它以所有 tap 首次报告的完整 arm 后渲染量子结束帧建立一次固定 barrier，并等待 SDL3 AudioContext 时钟与全部 tap 都到达该帧；首次可用帧较 arm 晚时，barrier 会覆盖这段初始化缺口。分批 status 响应期间时钟继续推进也不会移动目标。原始时钟、barrier依据、tap 身份与采样轮次随输入会话保存；按键和 PCM 判据仍使用各自的真实输入边界与完整 source 区间。

通过要求本次输入对应的唯一 voice 在自身生产输出上出现非零 PCM；源节点区间必须在会话关闭帧之前完整结束。完整区间持续为零判失败，采集缺段、溢出、来源或生产路由不明记 incomplete。后续节点、其他 tap 和输入前的声音各自保留身份。该场景证明输入关联的实际输出；精确延迟、资源编号、全部玩法音效及曲目分轨由各自场景汇总。

### AUDIO-06 | 高刷新与音频事件分开

- 操作：在 60 Hz 与更高刷新设置下，以相同逻辑输入和回滚样本触发同一音效。
- 观察与独立预期：将原生实际音效事件身份/数量和输出 PCM 起点与逻辑事件对应，独立参考是一项逻辑事件对应的声音事件。
- 判定：额外绘制帧不增加音效事件；回滚重演不重复播放已确认事件。
- 反例：仅提升显示刷新率便使一次击中发出多次声音，应失败。
- 当前入口/边界：共用 paired Replay 场景以生产帧回调分别运行 60／120／144 Hz 时间序列，逐逻辑帧核对真实 SFX 事件与输出路由的身份、顺序和数量，并检查额外绘制产生零次音效事件、路由或上传。报告记录本次事件窗口与实际回滚窗口；普通单机刷新率场景生成事件对照证据，MP 回滚由对应联机旅程记录。

原始音频证据使用 `audio-output/4`，将声源观察编号、采样槽代次、开始／停止／结束边界和 source／merge 两路 PCM 回执关联。采样槽在原声源结束且原始回执完成后复用；每个逻辑步等待本步采样完成，再推进下一步。判定器核对同一 voice 的窗口独占性、停止操作的时钟边界及每代回执，直接定位槽位竞争与来源缺口。每个事件要求连续、同代且可归属的非静音输出；全静音、断连、额外声源、重复事件与额外绘制发声均使该项失败。

音频验证按要求分工：

| 要求 | 实际观察与独立预期 |
| --- | --- |
| AUDIO-06 | 相同 Replay 的事件序列与次数一致，每个事件对应一个实际声源及非静音输出，额外绘制零事件。 |
| AUDIO-02 | 正式包输出 PCM 起点早于实测混合队尾下界，延迟反例由同一判据拒绝。 |
| 增益模型 | 受控未来帧离线渲染逐点等于独立的 float32 增益方程。 |

判定报告使用 `audio-assessment/2`，明确标记事件／声源／输出守恒职责。即时游戏调用的增益方程对照保存在 `gainTimelineDiagnostic`，逐项记录匹配数量和首个差异帧，原始 PCM 随报告保留。[AudioContext 时钟](https://www.w3.org/TR/webaudio/#dom-baseaudiocontext-currenttime)按渲染块推进，主线程调用前后时钟描述调用区间；渲染线程决定实际生效采样点。该诊断与事件守恒、实测延迟和受控增益校准分别记录。静音续段承担故障定位，首窗保留实际输出要求。

配对样本的 `audio.events` 保存音效编号整数序列，完整原生事件由 `audioOutput.raw.native.events` 保存。增益操作记录使用 `gainMutations.args:[value,time]`，与 `gainCalls` 的参数及调用前后时钟逐项对应。每次 `voice-pool-stop` 都保留回执，`nodePresent:false` 表示本次调用没有活动声源，节点停止与结束由各自的代次记录证明。

### MIDI-01 | 声明 MIDI 选项

- 判定：声明支持时选项存在且具备资源/传输路径；不支持时不提供不可用 MIDI。
- 反例：能力声明为不支持却显示可选 MIDI，或支持项被错误隐藏，应失败。
- 当前入口/边界：th08 driver 核对产品能力声明，并调用 Launcher 的正式 `createMidiBridge` 工厂和 TinySynth vendor fixture 验证真实 Runtime MIDI 事件可送达合成器。`tests/browser/test-music-selection.py` 使用 Runtime protocol stub 检查 Launcher 模式选择、本地 OGG 资源安装与回退流程；它承担选择与资源流程，不承担 MIDI 声音证据。

### MIDI-02 | 可听到的 MIDI 输出

- 操作：选 MIDI 并进入原表指定场景，触发已知曲目。
- 观察与独立预期：保存 Runtime 输出的 MIDI 字节流，并采集合成器实际 PCM；将曲目消息与同一资源的独立 MIDI 序列对应。
- 判定：输出包含正确曲目事件且合成 PCM 非静音；只发出事件或 MIDI 设备存在不等于可听。
- 反例：合成器调用被发送但没有连接到音频输出，PCM 仍为静音，应失败。
- 当前入口/边界：`--suite=music` 选择 `tools/ports/music-browser.mjs`；当前登记的真实 MIDI Runtime 场景为 th08 normal。正式包观察标题 SMF `bgm/th08_01.mid`、原生 Note 消息、Launcher MIDI bridge 发送字节和 TinySynth AudioContext PCM。原生事件与 TinySynth 成功发送的字节按事件顺序逐项核对；输出窗口与原生源身份共同判定。该窗口验证实际桥接输出与可听 PCM。th06／th07 的静态 transport 接线检查与该 Runtime PCM 场景分开记录。

### MIDI-03 | MIDI 生命周期

- 操作：在曲目播放时切曲、暂停、重开并退出，捕获每个转换前后的 MIDI 消息与合成 PCM。
- 观察与独立预期：把 Note On/Off、控制器重置、合成器活动音符和本作阶段对应；边界预期由原版行为或正式音乐规则给出。
- 判定：暂停/退出按本作设计停止或挂起，重开与切曲恢复正确曲目，没有遗留音符。
- 反例：退出后仍有旧 Note On 声音，或暂停时旧音符悬挂，应失败。
- 当前入口/边界：th08 normal 正式包记录 MIDI 原生 tick 在游戏暂停期间继续推进，并核对模拟隐藏后的合成器挂起及恢复；该来源状态符合 `MusicCommands` 的暂停路径。退出时沿用 `shell.mjs` 的 stop/close 与 relaunch 路径，核对 OGG Runtime 输出静音、Launcher bridge 收到 close、TinySynth `reset` 清空活动 voice，并由 bridge 停止 `_note` 创建的全部仍活动 source、重建完整湿支路；关闭边界保留首个活动 voice 清零回执，并验证同一边界内后续 reset 也保持清零。每个实际 source 的 channel、note、AudioNode 类型、start／stop 时间和 `ended` 事件随 close snapshot 保存。压缩器输出与 `TinySynth.out` 乐器源的并行 PCM tap 以相同采样时刻核对完整八窗静音；最终混音全零证明停止，乐器源全零用于同步定位音源状态。关闭到重开之间没有新 MIDI 消息。新节点保留原冲激响应、归一化和增益，随后同一 frame 的标题曲重新发送 Note On／Off 并产生 PCM。完整曲目切换与每首歌的 Note Off 表由其他场景验收。`midi-bridge.test.mjs` 覆盖 bridge 的 focus、pagehide、dispose 和关闭后的音色恢复。

### MIDI-04 | MIDI 与 OGG 分开

- 操作：移除 OGG 后选择 MIDI并播放，再恢复 OGG 文件，切回 OGG重新播放。
- 观察与独立预期：分别核对有效模式、资源请求和实际 MIDI 消息/OGG PCM；两类资源身份和读取路径独立。
- 判定：OGG 缺失不禁用有效 MIDI，MIDI 切换不复用旧 OGG 声音；安装 OGG 后选择 OGG 使用 OGG 轨。
- 反例：菜单变为 MIDI，但实际仍输出先前 OGG；或删除 OGG 导致 MIDI 也无法启动，应失败。
- 当前入口/边界：th08 normal 分别启动不挂载 OGG 的 MIDI Runtime 与新建 OGG Runtime，检查 MIDI 消息／TinySynth PCM 和已验证 OGG 源／Runtime PCM。两种声音路径由独立 configure 会话驱动；shell 在游戏运行时拒绝 `configure`，因此该场景不声称支持运行中模式切换。Launcher 控件与资源获取仍由正式 UI 验收。
