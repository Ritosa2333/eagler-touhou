# Artifact directory conventions

New artifacts are written under `artifacts/` according to purpose. Directory names describe retention and consumption rules, not verification status.

| Directory | Contents | Consumption rule |
| --- | --- | --- |
| `release/` | Complete candidates generated by `npm run release` | Must include a Release Manifest, checksums, and verification report; publication still requires explicit authorization. |
| `validation/` | Test sites, browser reports, and temporary package candidates | Reproducible; the formal publisher must not scan or select them implicitly. |
| `fixtures/` | Stable, manually reviewed test inputs | Tests consume them read-only; updates must document the affected contract. |
| `operations/` | Evidence from public deployment, cutover, and other external operations | Record the target, time, and corresponding release identity; never use as source or release input. |
| `snapshots/` | External or historical snapshots | Must record origin and capture time; never use as source or release input. |
| `tmp/` | Intermediate files without lasting evidentiary value | Formal builds must not read them; they may be removed after confirming that no consumer remains. |

DATA packages, WebKit smoke output, Runtime Storage evidence, working-tree inventories, and other reproducible integration results belong under `validation/`. The repository no longer maintains a separate test-distribution product topology; site-level validation reuses the formal self-host/release assembly path. Formal candidates are written to a new explicit directory by `npm run release -- --input=... --output=...`.

Historical `dist/`, `archive/temporary/`, and old `artifacts/` contents are not compatibility APIs. Formal builds must not select inputs from them implicitly. After delivery, reproducible outputs should be removed from the project directory or deleted. Release or acceptance evidence that requires long-term retention belongs in an explicit external evidence store and must record the corresponding release identity.

The following build directories are local-only, reproducible development or validation inputs:

```text
th06-eagler/build-web-eagler-default
th06-eagler/build-web-eagler-external
th06-eagler/build-web-eagler-thprac-test
th06-eagler/build-web-netplay-th06
th07-eagler/build-web-eagler-default
th07-eagler/build-web-eagler-external
th07-eagler/build-web-eagler-thprac
th07-eagler/build-web-th07-netplay
```

These paths carry no compatibility guarantee. Development source paths are owned by `lib/development-content.mjs`; the publisher neither reads these defaults nor searches the source root for generated manifests. A path may move together with all local callers in one coherent change. Directory-Runtime development paths are likewise implementation details rather than publication contracts.

## Build profile

Directory names do not establish build identity. `lib/development-site-manifest.mjs` generates the development Site Manifest from the workspace when needed and declares `web-development`; the source tree does not retain a second generated manifest. The publication Host seed contains neither machine-local paths nor a generated identity. The low-level `package-server.mjs` must receive a non-development profile. A server candidate's `site-manifest.json`, `deployment.json`, and Release Manifest use the same profile, and the top-level formal candidate is `web-release`. The verifier rejects profile mismatches between manifests and artifacts.

The two browser-visible manifests have fixed names and responsibilities. `site-manifest.json` describes Runtime and content identities, languages, music, and server capabilities. `release-catalog.json` describes only installable Package revisions and Package Descriptor URLs. The development server exposes the same two standard endpoints; an empty development Release Catalog is valid, and no third `games.json` protocol exists.

Site output is always a flat, relocatable deployment root: `index.html`, `site-manifest.json`, `release-catalog.json`, `assets/`, `runtime/`, `games/`, and `shared/` live directly in that directory. Artifacts do not embed `/eagler-touhou/` or any other public mount path. Servers mount them at `/` by default; a subpath is an explicit server configuration and does not require repackaging the site.

When migrating the historical `/eagler-touhou/` mount to `/`, the server temporarily owns a bounded compatibility layer. The two old entry URLs redirect to `/`. The old-scope `app-shell-sw.js` returns a non-cacheable retirement Worker that unregisters itself and navigates controlled windows to `/`. During retirement, all other old subpaths map to the same flat site so a stale cached page cannot receive HTML in response to a JSON request. This layer is not a second public mount contract. After clients carrying the published old Worker have naturally aged out, remove both `legacy-mount-retirement-sw.js` and the corresponding server rules.

Build scratch defaults to the operating system's temporary directory. Staging that must share a filesystem with the final directory for atomic cutover belongs under `.tmp/` in the target's parent directory. A failed candidate worth retaining for diagnosis belongs under `.release-incomplete/` and must not masquerade as temporary data. Formal candidates must not contain `.tmp`, `.staging`, `.next`, temporary configuration, or ad hoc SSH files.

The profile expresses artifact authority: `web-development` and `web-validation-*` are only for local development or validation, while only `web-release-*` may enter a release candidate. Resource mode is an independent dimension with three formal values: `hosted`, `external`, and `import`. `hosted` publishes Runtime and game payloads. `external` publishes Runtime, the Release Catalog, and Package Descriptors while infrastructure redirects game and shared payload routes to an external origin. `import` carries no game content, Runtime updates, or Release Catalog entries because players provide complete packages themselves. Historical `import-only` and `import-partial` values belong only to old deployment snapshots. The Launcher and verifier retain bounded read-only compatibility; new configuration, packagers, and release artifacts emit only the three formal values.
