# WEB 1.0.9：浏览器时间戳边界导致的空帧

用户继续报告四、五、六面掉到三十多帧，以及部分阶段持续约 50 帧。此次确认并修复了真实运行循环中的一个调度缺陷；这不是全部手机性能问题已经消失的证明。

## 已复现的问题

`BrowserRuntime.cpp` 使用固定 60 Hz 累积时钟。旧版严格向下取整，只容许 1 纳秒误差；当刷新时间戳落在更新边界前一点时，该次刷新没有更新、也没有提交画面，下一次却连续更新、绘制两遍。

在不可变的 1.0.8 开发构建上，直接调用正式 C++ RAF 回调，分别输入 0.1 毫秒取整、1 毫秒取整、±0.4 毫秒抖动三组时间戳。每组 600 次刷新均产生 600 次逻辑更新、400 次画面提交、200 次空回调、200 次双重更新。这可以在逻辑速度正常时造成不必要的显示卡顿，并把密集消弹的两帧 GPU 工作集中到一次刷新中。

这是可重复的代码缺陷和候选原因。没有取得用户手机的逐帧时间戳，不能据此断言其所有 30/50 帧场景都由它造成。没有发现专门锁 50 帧的代码。

## 修复

TH17 在固定时钟边界使用最多 1 毫秒容差，提前使用的时间保留为负余额，后续偿还。重复时间戳不会额外推进游戏；50 Hz 屏幕也不会使游戏加速。长停顿的工作量上限、暂停后清空积压、原有录像输入均保留。其他游戏默认容差仍为零。

同样的三组真实循环测试，修复后每组为 600 次逻辑更新、600 次画面提交、零空回调、零重复绘制。WASI C++ 测试另覆盖 15、20、30、50、59、60、75、90、120、144、165 Hz、取整、抖动、借用时间偿还、重复时间戳和长停顿。

此次生产改动仅涉及浏览器循环及其固定时钟；游戏、渲染、音频源码与 1.0.8 的哈希逐项比对。仍使用 SDL3/WebGL2、默认 1280×960、完整弹幕和效果。

## 验证方式及范围

- `scripts/verify-browser-cadence.mjs`：真实 BrowserRuntime RAF 回调，旧版和新版三种时间戳对照。
- `scripts/profile-browser-replay.mjs`：原版 `Th17_ud0134.rpy`，1280×960、音频开启，在四面 14761–15301、五面 15001–16201、六面 18301–19801 测量真实运行循环。准备阶段允许加速定位，测量阶段仅由正式 RAF 循环推进。
- 额外根据 1.0.8 全程采样的热点补测五面 13021–14461、六面 23701–24781，覆盖截图之外的较高负载窗口，数据单独保存在 `browser-replay-expanded-1.0.9`。
- `scripts/verify-browser-performance.mjs`：对照这些窗口的游戏、视觉随机数及完整暴露状态，并核对 Extra 完整保护输入回归的 81228 次更新。保护输入只用于开发测试，不属于无作弊原版录像证明。
- 1.0.8 的一至六面完整录像证据仍保留旧构建身份。本次没有把这些历史报告改写成新的全程手机测试。
- 正式构建另检查无开发入口、文件哈希、启动、暂停、返回菜单、存档及公网资源身份。

原始数据保存在 `artifacts/performance/browser-cadence-baseline-1.0.8`、`browser-cadence-final-1.0.9`、`browser-replay-1.0.9`、`extra-cadence-1.0.9`。发布身份以 `reference/release-acceptance.json` 为准。

## 未达成的验收

四、五、六面的测试窗口中，桌面 RAF 提交平均约 60 次/秒，没有再次出现空回调后双重绘制。但异步 GPU 计时仍有超过 18.18 毫秒的样本；RAF 提交频率不能证明显示器实际呈现速度，更不能代表用户手机。因此 `phone55fpsAccepted` 保持 `false`，不宣称手机全程最低 55 帧已经达标。

补测五面热点时出现两次约 33.3 毫秒的真实刷新间隔，随后按原规则补回逻辑更新；该窗口平均提交率约 59.92 次/秒，GPU 最大样本约 31.14 毫秒。这与已修复的“刷新回调正常到来却被时钟空过”不同，仍属于尚未满足最低帧率预算的证据。五个窗口共 96 个游戏状态检查点一致；Extra 完整回归摘要为 `29cc1179db215873f366b4e173dd0208679025373f0293bbd2f008eb4f2c4a72`。
