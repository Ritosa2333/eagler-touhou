# WEB 1.0.10：持续 50 帧复查与消弹内存分配

用户在 WEB 1.0.9 仍遇到四、五、六面掉帧，以及某些阶段稳定约 50 帧、随后恢复 60 帧。此次确认上一版的时间戳测试范围不足：只测了小于 1 毫秒的抖动，遗漏了超过其容差的刷新相位变化。

## 可重复的 50 帧缺陷

在不可变的 1.0.9 开发构建上，通过实际 C++ `BrowserRuntime` RAF 回调，输入十秒内 600 次刷新，其中每六次有一次分别提前 1.1、2、4、6 毫秒。四组均得到 600 次逻辑更新、500 次画面提交、100 次空回调及 100 次双更新。因此即使浏览器提供平均 60 Hz 的回调，旧调度也能自行造成稳定 50 次/秒提交。

这是受控时间戳下的实测代码缺陷，不是从用户手机采集的时间序列；不能推断手机所有掉帧均由它引起。网页前端及 C++ 调度没有找到独立的 50 帧限速配置。

新调度取最近的固定 60 Hz 时钟点，最多允许半个逻辑帧的时间偏移，提前使用的时间保留为负余额并偿还。相同的四组测试加上原有三组取整/轻微抖动，共七组均为 600 次逻辑更新、600 次画面提交、零空回调、零双更新。暂停、重开、重复时间戳和长停顿处理保持原有约束。15–165 Hz 的量化时间戳，以及 60→120→50→90→60→144→59→60 Hz 的动态切换均检查逻辑时钟没有累计加速。

## 密集绘制的额外开销

共享渲染器的加法合批原先每次 flush 创建嵌套 vector，为许多单独保留的 draw 也分配一个很小的堆块，随后全部释放。密集消弹、世界精灵和拖尾交替时会重复这种工作。

改为复用连续的分组、索引链和重排缓冲；每个分组仍按原来的内部顺序复制与提交。可合批条件、透明混合、深度读写屏障、全部弹幕及效果、实例数据、1280×960 默认分辨率均不变。其他作品默认未启用 TH17 的加法合批，固定时钟默认容差也仍为零。

## 验证和证据边界

- `scripts/verify-browser-cadence.mjs` 对照实际 C++ RAF 回调；旧、新两份报告分别在 `artifacts/performance/browser-cadence-baseline-1.0.9-expanded` 和 `browser-cadence-final-1.0.10`。
- `scripts/profile-browser-replay.mjs` 重新跑用户的原版 `Th17_ud0134.rpy` 六关，共 135,033 次更新、每次保留绘制，1280×960，音频开启。此完整覆盖使用受控 4 毫秒相位偏移；虚拟时间算出的提交频率不作为实时性能结果。
- 完整录像通过顺序更新索引，与不可变 1.0.8 全程采样中的 24 字状态（含游戏及视觉随机数）比较，2,254 个检查点全部一致。过关时场景帧计数会重置，不能仅凭帧计数查表而漏掉过渡尾部。
- Extra 重新运行 81,228 次更新的固定保护输入流程，包含三个实际炸弹输入、实际关底与消弹。摘要 `29cc1179db215873f366b4e173dd0208679025373f0293bbd2f008eb4f2c4a72` 与参考一致。此项不是无作弊原版录像测试，音频关闭。
- 182 个 1280×960 逐像素检查覆盖一至六面及 Extra 开头、四面消弹扩展窗口和六面密集激光，同时检查状态及随机数；比较的基准构建身份保留在报告内。
- 实时耗时对照与上述并行覆盖分开运行，使用相同的四、五、六面窗口、音频和分辨率，记录 CPU、异步 GPU 与真实 RAF 间隔。原始数据分别在 `browser-realtime-baseline-1.0.9` 和 `browser-realtime-final-1.0.10`；不把虚拟时钟的 60 次/秒写成真机 60 FPS。
- `scripts/verify-browser-performance.mjs` 核对构建身份、未改动的游戏及音频源码、完整状态检查点、像素报告以及实时测量。正式包另检查资源哈希、无开发入口、桌面及手机视口启动、暂停恢复和公网版本。

手机全程最低 55 帧未取得物理设备测量，因此 `phone55fpsAccepted` 保持 `false`。本次可以确认的是可重复的 50 帧调度缺陷得到修复，以及合批的临时小块内存分配被移除；不能将功能/画面对照或桌面采样当成物理手机最低帧率验收。

发布身份与最终验收记录见 `reference/release-acceptance.json`。

正式 WEB 1.0.10 已发布并通过公网完整 Wasm 哈希及新浏览器会话的实际游戏启动、暂停恢复、返回标题检查。发布清单 `20e1c7e172cd136b36feb065`，正式 Wasm SHA-256 `e6818c30af017a7558e6eaf0c8d0373f8529bb244ef644a08ce5a08d07de05e8`。旧版完整保留在 `artifacts/release-before-1.0.10`；开发验证构建保留在 `artifacts/performance-final-1.0.10`。

## 实时测量结果

相同桌面机器先旧后新、串行运行，均为 1280×960、音频开启。表内为 CPU 平均耗时；短窗口和单次测量不是统计意义上的设备性能保证。

| 窗口 | WEB 1.0.9 | WEB 1.0.10 |
| --- | ---: | ---: |
| 四面 14701 起 900 次更新 | 4.33 ms | 3.29 ms |
| 五面 13021 起 9600 次更新 | 2.52 ms | 2.01 ms |
| 六面 18001 起 7200 次更新 | 2.89 ms | 3.61 ms |

六面长窗口的 CPU 结果较差，因此另用反向顺序（新→旧）、固定每次一次完整应用更新的方式，复测六面 18301 起 1500 次更新以隔离调度。新/旧 CPU 平均值为 3.39/3.25 ms，P95 为 6.64/6.60 ms；GPU 平均值为 9.38/9.57 ms。该结果未重复长窗口约 25% 的差距，也不能证明六面有明确速度提升。逐批绘制工作量和状态一并对照；两次测量均保留，不选择性隐藏较差结果。

新版三个实际 RAF 窗口的一秒滚动提交率最低值约为 57.05、58.03、60.00 次/秒，未发现持续 50 次/秒区间。这是桌面提交率，不是 GPU 完成率或手机 FPS。四面有三个真实 33.3 ms 刷新间隔；五面通关切换仍出现约 52.79 ms CPU 样本，GPU 也有超过 18.18 ms 的样本。因此严格的逐帧预算和手机全程 55 帧仍没有被标为通过。
