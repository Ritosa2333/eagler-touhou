# TH11 多人整堆回滚

TH11 MP 将游戏对象、动态容器和分配器元数据放在同一套恢复边界内，通过最终 Wasm 的写入日志恢复整帧状态。新增游戏字段或调整容器时，位于已登记区域内的写入会自动进入日志，减少逐个子系统维护快照字段的工作。网络输入、确认输出和资源退休继续使用当前多人运行时的边界。

方案参考 [TH11 源仓库 issue #7](https://github.com/Ritosa2333/th11/issues/7) 和 [apeirs/th11 的固定版本实现](https://github.com/apeirs/th11/tree/324fb143e78560ae34f5930a19048e34035eb2f8)。本作接入公共 [`WriteJournal`](../../../common/include/eagler/netplay/WriteJournal.hpp)，沿用现有 12 帧预测上限、输入协议和多人规则。构建步骤见[开发指南](DEVELOPMENT.md)，运行结果见 [2026-10-23 验收记录](rollback-20261023.md)。

## 状态由谁恢复

“整堆”指专属游戏模拟堆。恢复范围由模拟堆和 `GameSession` 根对象共同组成，宿主服务按自己的生命周期管理。

| 状态 | 所有权与恢复方式 |
| --- | --- |
| 游戏对象、敌人和 ANM VM、对象池、标准容器、随机数与逻辑计时状态 | 动态对象位于固定的 192 MiB 模拟堆；根对象中的成员位于单独登记的 `GameSession` 范围。两个范围都由首次写入日志覆盖。 |
| 分配器元数据 | dlmalloc mspace 元数据与游戏分配位于同一模拟堆。恢复对象内容时也恢复分配、释放和空间复用状态，使重模拟可沿原分配顺序使用地址。 |
| 渲染器状态和纹理像素 | 保留已有 `RollbackJournal`、纹理事务和资源租约。恢复 CPU 像素后同步 GPU，刷新派生绘制缓存；GPU 句柄继续由图形设备管理。 |
| 字体、图形设备、长期资源缓存、网络通道 | 使用系统分配，生命周期由宿主拥有。字体光栅化产生的可见纹理修改仍进入纹理事务。 |
| 音效、音乐命令、Replay 与旁观输出 | 使用系统持有的逐帧记录，纠正时重新生成，连续确认后按帧发布。 |
| 本地判定点显示与本地玩家可见性设置 | 恢复前保留用户当前选项，恢复后重新应用。 |

[`Application::initialize`](../web/cpp/sdl/Application.cpp) 登记 `&session` 和精确的对象大小，并在 `GameScope` 中原地重建 `GameSession`，让初始容器也获得游戏所有权。根对象首尾不足 32 字节的部分按真实范围裁剪，宿主相邻字节保持其自身状态。

[`GameScope` / `SystemScope`](../../../common/src/netplay/WriteJournal.cpp) 负责分配路由：前者使 `new`、`new[]` 与对齐分配进入模拟堆，后者使宿主服务使用系统堆。释放操作按指针实际所属区域选择分配器，不依赖释放时的作用域。ANM 几何和 ECL 等原始分配入口使用对应的游戏分配辅助函数。作用域可以嵌套，并在退出时恢复先前的所有者。`SystemScope` 中对既有游戏对象的修改继续进入写入日志，适用于同时访问游戏与宿主状态的调用链。

[`HostScope`](../../../common/include/eagler/netplay/WriteJournal.hpp) 在系统分配的基础上暂停写入追踪，使纯宿主绘制工作避开逐次写入的过滤调用。每个入口及其下游调用都要求不写入或释放模拟堆、根对象，也不调用游戏回调。已审查的接入范围如下：

| 入口 | 追踪暂停的范围 |
| --- | --- |
| [`GraphicsDevice`](../web/cpp/sdl/GraphicsDevice.hpp) | 纹理绑定、顶点布局与矩阵提交、三角形与图元提交、视口、清屏、呈现，以及渲染目标选择和清理。顶点和矩阵输入按只读数据使用。 |
| [`AnmRenderer`](../web/cpp/game/AnmRenderer.cpp) | 宿主顶点队列、材质缓存、四边形与 ASCII 图元提交、多人透明度副本，以及刷新和失效处理。 |
| `AnmRenderer::set_camera` | 游戏相机计算完成后的局部块，复制渲染器相机并提交矩阵和视口；原作相机计算继续追踪。 |
| [`stage_visible()`](../web/cpp/game/StageDraw.cpp) | 输入只读、临时几何结果位于栈上的可见性判断，返回 `bool`。 |

`AnmRenderer::draw()` 的 VM 修改、Draw 回调、字体布局与纹理像素读写沿各自原有日志路径执行。带结构体返回值的通用几何函数需要单独检查调用方的返回缓冲区归属，不能据其局部计算形式直接暂停追踪。`HostScope` 保持帧事务开启；嵌套退出时恢复进入前的追踪开关，帧已关闭或发生终止性错误时保持关闭。

## 每帧记录实际写入

[`WriteJournal.cpp`](../../../common/src/netplay/WriteJournal.cpp) 将恢复范围分成 32 字节块。一个块在同一逻辑帧第一次被写入前，保存改写前的字节；后续写入复用该帧的标记。每帧日志量由实际改写的块决定，192 MiB 是模拟堆容量。

最终链接产物经过 [Wasm 插桩器](../../../tools/rollback/README.md)，覆盖整数、浮点、完整 `v128` 存储及 `memory.copy`、`memory.fill`、`memory.init`。原始操作数先按既定顺序求值，再记录目标区域，最后执行写入；这也覆盖编译器内联后的赋值和容器操作。范围过滤根据写入地址判断，跨 32 字节块或跨恢复区域边界的写入保留相交部分。

正式构建使用 `--native-filter`：写入点检查追踪开关与非零长度，并保留有效地址溢出检查；模拟堆与根对象的范围判断集中在不参与插桩的 `eagler_rb_touch` 中，减少各写入点重复的指令。范围外写入直接返回；同帧已经记录的标量写入检查首尾块后返回，未对齐写入也覆盖两个块。插桩器默认的 Wasm 范围过滤配置与此配置使用同一组真实 C++ 场景验证。

需要保存首次写入内容时，入口先暂停追踪，再调用 `eagler_rb_capture`。这个单独保留的冷捕获导出使最终链接优化保留较小的高频入口，完整捕获循环位于辅助函数中；插桩器和打包器的三个必需导出约定保持原样。

恢复到帧 `f` 时，从最新帧开始逆序写回日志，得到 `f` 开始前的游戏对象与分配器状态，然后使用输入核心保存的输入重模拟。日志自身位于系统内存，记录过程中暂停追踪，避免递归记录日志的写入。记录容量与失败状态有明确检查；部分记录失败不会被当作可恢复帧使用。

`Clear()` 在帧已关闭的边界清空历史；遇到未封帧事务时，将后端置为终止失败，并保留首个错误原因。Wasm 越界陷阱会跳过 C++ 析构，因此清理依据 `FrameOpen()` 的事务状态判断，覆盖 `HostScope` 已暂停追踪而事务仍开启的情况。JavaScript 捕获陷阱后调用清理，后续 `Ready()` 和 `BeginFrame()` 均拒绝复用该实例的未完成状态。

## 一次事务覆盖 Update 与 Draw

[`MultiplayerRollback.inc`](../web/cpp/sdl/MultiplayerRollback.inc) 将游戏更新、文字像素处理、原作 Draw 和封帧放在同一事务中。Draw 会推进部分原作表现状态，因此历史帧也执行完整的 Update 和 Draw。

1. 输入核心准备当前帧的各席位输入；宿主创建逐帧输出记录。
2. 开启游戏写入日志、纹理事务和渲染状态日志。
3. 更新游戏，将音频事件复制到系统记录，处理文字，再执行原作 Draw。
4. 封存三个恢复部分，随后标记该帧已模拟。

封帧直接通过 `LastFrameBlocks()` 读取 `EndFrame()` 已维护的块数，统计开销为常量时间。完整 `Stats()` 会遍历分配器块以计算堆占用，留在诊断查询路径；每个模拟帧的封帧路径无需扫描堆。

纠正开始前先清空已排队的绘制工作、取消待提交的呈现，并验证纹理资源租约。随后恢复模拟内存、渲染状态和纹理，重建派生缓存，丢弃待重模拟区间的旧输出记录。音频记录使用系统内存副本，避免宿主持有会被分配器恢复覆盖的游戏容器。

阶段更替、资源替换、暂停与菜单等生命周期操作继续使用现有确认屏障。事务内遇到边界时先撤销本帧游戏修改，保留已采样的本地输入；待历史对账完成，再沿全部输入已确认的路径执行边界操作。`WorldRollback::CanCapture()` 与边界请求仍承担这一准入职责。

## 网络推进与输出提交

网络通道、已采样输入、ACK、重传和输入确认前沿由 [`NetplayRuntime`](../web/cpp/multiplayer/NetplayRuntime.cpp) 持有。恢复游戏帧后，历史模拟消费已保存输入；物理输入采样时钟继续向前。

提交由“输入已确认”和“纠正已完成”共同决定。驱动先退休对应的原始撤销记录，再释放纹理租约，最后开放连续的输出提交水位：

- 音效及音乐命令按帧执行一次；淡出和效果处理每个已确认逻辑帧推进一次，包括没有音效的帧。
- Replay 追加纠正后的已确认输入；分数和结束状态沿同一水位发布。
- 旁观者读取纠正完成后的连续已确认历史。

纯延迟模式、只读 Replay 和旁观播放使用各自现有的精确推进路径。此后端由 TH11 MP 构建显式启用；普通 TH11 使用独立的源码和构建入口。

## 构建身份与验证

[`portable/build.mjs`](../portable/build.mjs) 将模拟堆分配器、插桩器及其锁文件纳入构建输入，最终 Wasm 插桩后再生成运行包。初始化核验 `0x52424a31` 标志；[`package-eagler.mjs`](../portable/package-eagler.mjs) 核对 `stateBackend=write-journal-32`、插桩版本、三个导出与唯一的 `eagler.write-journal.v1` 自定义节，并核对最终文件身份。

共享后端由 `EAGLER_WRITE_JOURNAL=1` 显式启用。`WriteJournal.cpp` 与 `SimulationHeap.cpp` 在宏未定义或为 `0` 时不产生定义符号，让其他产品保留自己的分配器和运行路径。测试分别编译这四种真实 Wasm 对象组合，再用启用后端的 19 个独立实例验证恢复、异常与初始化拒绝行为。

验证按各自职责组织：真实 Wasm 指令测试检查写入语义，C++ 测试检查分配器与恢复范围，包测试检查交付身份，双客户端浏览器检查已纠正的原生状态、生产 Replay 和同帧画面。可重复执行的命令与明确的运行环境见[验收记录](rollback-20261023.md)。

后续增加游戏状态时，先确定对象所属区域；需要跨越预测历史的宿主资源继续保留租约与确认屏障。由 JavaScript 直接写入线性内存的桥接入口需要显式接入记录，或使用系统内存承载输入，再由 Wasm 更新游戏对象。模块内的写入覆盖由最终产物插桩统一维护。
