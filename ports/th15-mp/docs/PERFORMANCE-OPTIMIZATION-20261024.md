# TH15 MP 回滚性能优化与复测（2026-10-24）

本轮处理了三项具体开销：恢复时重复上传未修改的纹理、设备绘制路径进入模拟写入过滤器、历史追赶消耗新逻辑帧的时钟额度。实际状态／像素 oracle 的六组验证全部通过；诊断中的暖机战斗窗口从每席约 137–146 MB 纹理上传降为零。正式生产包的六场无 profiler 测量则显示：**双人 mode 0 的新逻辑推进从 17.27 提高到 21.13–21.53 帧／秒；整体 100 ms 长停顿门槛仍为 0/6，三人场景存在明显停顿。**

运行观察为 6/6，原始保存综合检查为 5/6。独立核对的实际文件字节和原运行的 native 文件校验为 6/6；另一项“测量窗口结束后、与显式保存并发提交的右移＋射击进入确认 Replay”的证明为 5/6。这些结果分别记录，不用文件一致性替代完整输入证明。

本报告接续[第一轮生产包性能记录](PERFORMANCE-20261024.md)。逐席指标、源码与产物身份、原始回执和独立审计索引见 [PERFORMANCE-OPTIMIZATION-20261024.json](PERFORMANCE-OPTIMIZATION-20261024.json)。代码位于独立分支 `experiment/th15-rollback-20261023`。

### 计时口径

新逻辑帧按观察到的最大 `NextFrame` 水位统计，历史重演不会重复计入新进度。完整回调包括真实 Emscripten 游戏 rAF 的全部执行区间，包括没有 `onGameFrame` 通知的历史追赶。画面提交计数默认 DRAW framebuffer 的颜色 blit；它不是 GPU 完成时间或显示器扫描帧率。

100 ms 门槛同时检查完整回调最大值、画面提交间隔和新逻辑水位停顿。跨越窗口末端的回调保留完整耗时，画面和水位间隔则在窗口边界截断。代码中的每次恢复驱动最多 4 帧／4 ms、外层 16.67 ms 都在完整调用之后检查，属于软预算，不构成单帧耗时上限。

本轮 callback 后的状态 observer 各席 P95 为 0.7–10.7 ms，最长一次为 241.3 ms；每席窗口内 observer 累计占固定窗口约 0.31%–3.28%。外壳及轻量钩子仍在完整回调中计时。这些都是墙钟时长，不能相加分位数，也不能称为无开销观察。

## 三项实现

### 仅刷新曾被 CPU 修改的纹理

原实现以“像素属于模拟堆”判断恢复后是否需要刷新设备缓存。预加载的 ANM 像素也在模拟堆中，因此每次恢复会使大量从未修改的贴图重新上传。

`GraphicsDevice::Texture` 现在保存设备侧的 `cpu_mutated` 标记，真实 `changed()` 将其置位，并一直保留到资源卸载。恢复时对这类游戏堆图像刷新缓存；未修改的 ANM 图像继续使用原上传内容。标记不随预测状态撤销，所以第一次修改恰好发生在被放弃的预测帧中时，恢复仍会刷新正确像素。

真实字体写入、清图、PNG 上传、复制和重采样写回路径已经核对。定向 oracle 在第 240 帧打开实际 journal 时，通过真实 `clear_image` 修改一个 16×16 纹理，然后经真实上传和 GPU 读回检查；撤销后 CPU／GPU 的四个摘要都恢复基线并与准确输入实例一致。编辑和恢复分别上传 1,024 字节，未修改的对照纹理保持零上传。这项定向用例覆盖首次图像修改；它没有直接执行 `FontDevice::text` 或 `Renderer::read` 的所有写入组合。

### 设备绘制使用 host scope

经逐条检查的 `Renderer` 和 `PresentationFrame` 设备缓存、上传、绘制指令记录、恢复及提交路径使用现有 `WriteJournal::HostScope`。这些对象由系统堆持有，进入这类作用域时暂时关闭逐写入的模拟地址过滤，退出时恢复配置，嵌套作用域保持平衡。

写回游戏像素的 `Renderer::read` 保持跟踪；字体与游戏绘制回调中的模拟修改仍被记录。性能窗口包含实际原生 Update、Draw 和历史绘制，完整画面与游戏状态由 oracle 对照；GL 调用路径和顺序由代码审查确认未改动。

### 历史追赶保留前推时钟额度

回滚模式使用基于公共 `PendingFrameSchedule` 的 `FrameSchedule`。只有真正发生 `mp_advanced` 才消费一个新逻辑帧额度；历史重演、恢复完成交接和 CPU 分批让出会退回本批尚未完成的额度，且只退回一次。

真实缺失输入或保存确认等待保留一次已经到期的重试和小数相位，等待期间的墙钟时间不形成后来突然连续采样的额度。每次真实 rAF 的时间倍率只应用一次，每次 rAF 最多四次调度调用、100 ms 债务上限、12 帧预测窗口和原有软预算保持约束。暂停、启动、停止、加载、world 重建和模式切换清理相关时钟。

普通模式、mode 1、只读 Replay 与旁观继续使用已有 `PracticeCadence`。原生测试把适配器与实际 `NetplayRuntime`、输入通道及 `PendingSave` 组合验证，共 13 组、20,605 项检查通过；生产 rAF 集成由本轮正式包运行覆盖。

## 诊断与剩余成本

三次 mode 2／双人诊断分别使用原生产包、纹理＋host scope 优化包、再加入时钟修复的包。各次都是独立 15 秒窗口，开启 4 ms CPU 采样和 GL API 包装，明确标记 `performanceEligible:false`、`thresholdsMet:null`，不作为正式性能成绩。

| 诊断阶段 | 两席纹理上传 | 两席完整回调 P95 | 两席完整回调最大值 | 两席新逻辑帧／秒 |
| --- | --- | --- | --- | --- |
| 原生产包 | 146.06／137.25 MB | 44.1／30.4 ms | 244.7／111.4 ms | 22.07／22.00 |
| 纹理＋host scope | 0／0 | 23.0／26.2 ms | 66.7／56.3 ms | 22.47／22.00 |
| 再加入时钟修复 | 0／0 | 26.2／28.2 ms | 50.4／54.9 ms | 24.07／23.87 |

MB 为十进制字节。原生产包上传的约 99.50%／98.88% 发生在恢复或历史重演回调中，每次恢复约对应 6.9 MB。优化后零上传的结论限定于这些已暖机的战斗窗口；字体新增、资源切换和完整流程的上传不由该窗口代表。第三次诊断仍实际执行了 23／32 次恢复和 81／95 帧历史重演。

最后一次诊断在 profiler 启动前、结束后分别读取浏览器进程累计 CPU 时间。两席 GPU 进程的 CPU 增量为 56.40／60.62 秒，查询中点跨度为 16.172833／16.186321 秒，对应平均 3.48733／3.74514 个 CPU 核。两者近同时平均值之和为 **7.23247 核**，全部浏览器进程为 **7.86042 核**，接近记录的 8 核 CPU 配额。浏览器报告渲染后端为 `ANGLE_SWIFTSHADER`。

这证明该诊断中软件 GPU 进程占用了大部分 CPU 预算。它不是硬件 GPU 执行耗时；两个快照区间略有差异，并覆盖 profiler 起止，不能写成 15 秒纯窗口 CPU 占用。没有采集该窗口前后的 cgroup throttle 差值，也没有给每个 rAF 间隔建立 CPU 归因。

继续减少历史帧的 GPU 提交，需要明确当前合成目标的覆盖、混合和纹理版本依赖。现有 `PresentationFrame` 保存绘制命令，没有完整的目标依赖或历史纹理版本契约；部分颜色／深度清除和保留目标颜色的操作需要额外证明。当前生产路径实际执行历史 Draw，其正确性由全分辨率像素对照维护。

### 原始输入证明失败

`final-mode0-2p-01` 的 seat 0 输入证明区间为 `[758,774)`。最终确认 Replay 共 798 帧，区间中的 16 帧全部存在，按钮均为 1：射击存在，右移不存在。Host 输入 ACK 早于 sync ACK，原规则要求右移与射击同时出现，因此原始 `saveValidationPassed:false` 保留。

该席 `scoreth15.dat` 为 30,149 字节，MEMFS／IndexedDB 的 SHA-256 均为 `26764f694fda54b8b47ad9a1a84752ba31988ffe9a78779c41a6bdd3ec1bf75f`；`th15.cfg` 为 108 字节，双方 SHA-256 均为 `f8811e02d6c1ad4103fed406734c481d6f3a77ddb637fa07bf00ea259edb1a20`。两文件记录的原生校验均通过。因此文件持久化与输入证明分别计数。

源码调查发现，`TouchController::sample` 仅在本地角色处于可移动状态、且场景没有禁止移动时输出摇杆方向，射击不受相同门控。原始记录没有序列化当时的 `life`／`ready`，所以不能据此断言该席当时处于某次死亡或复活。调查已经核对完整输入区间、ACK、释放、停止和导出顺序；两份最终 Replay 都显示第 758 帧从中性转为射击、第 774 帧松开，右移缺失仍按原规则记为失败。

### 明确输入变化的补充验收

验证器在提交 `a8984ae8b1e11a970f5784870366b2daadebe4d7` 改为先停止旧输入生产器、等待其全部 ACK，并对所有席位显式发送中性输入。确认前缀覆盖两帧后，完成正常 baseline-sync 并核验实际保存的 Replay；随后并发提交新的 fire 与 concurrent-sync，保留输入 ACK 早于该次 sync ACK 的硬要求。输入持续到确认前缀覆盖新的采样，再通过单独 evidence-sync 取得持久化证据。每个 Replay 必须完整覆盖证明范围，并核对全席位前缀、新的 `0→fire` 和后继射击帧；代数、延迟、席位归属、状态回退和超时均受检查。

生产 `_th15_mp_replay_save()` 使用固定路径，探针通过已经完成的正常 Host 保存取得 Replay，再将验证副本写入 `/tmp`。三次 sync 分别记录自己的请求和 ACK。取证验证实际 MEMFS／IndexedDB 中的分数、配置及 Replay 字节，并用原生 reader 验证；若另一轮保存启动而无法建立稳定快照，明确保留失败。原有停止生产者后的最终 Replay 导出仍单独保留。
