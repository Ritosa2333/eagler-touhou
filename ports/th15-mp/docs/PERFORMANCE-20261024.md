# TH15 MP 生产包性能实测（2026-10-24）

后续纹理缓存、设备写入跟踪与前推时钟优化，以及新的六场完整复测见[回滚性能优化记录](PERFORMANCE-OPTIMIZATION-20261024.md)。本文保留第一轮测量与自动存档修复的原始结果。

本次用正式生产包、每席独立的 Chromium 进程和真实 Relay，补齐了回滚的回调耗时、逻辑推进、画面提交、内存及存档证据。**在同机软件渲染、单向额外发送延迟 50±5 ms 的固定压力场景中，修复后的六场运行观察全部通过，预先规定的 100 ms 长停顿门槛为 0/6 通过。** 四个回滚场景的逻辑推进约为双人 16.3–17.3 帧/秒、三人 10.8–13.1 帧/秒。

本次还修复了实测发现的 30 秒自动存档错误。修复后的运行完成了实际存档持久化和保存期间的输入确认；这项修复没有构成帧率提升的证明。此前的 [回滚正确性验收](ROLLBACK-ACCEPTANCE-20261023.md) 与本次性能实测分别记录。

机器可读结果、逐席指标、文件身份和审计索引见 [PERFORMANCE-20261024.json](PERFORMANCE-20261024.json)。原始证据目录为 `th15-performance-20261024/`；原六场、一次因果诊断和新六场的回执均保留。

运行观察要求源文件和生产包身份稳定、没有游戏运行错误、输入得到确认、各席原生 Replay 的共同输入前缀一致，并且回滚模式实际执行了恢复与历史重演。六场均满足这些检查。纯延迟的恢复和重演计数均为零；回滚场景每席在窗口内记录到 20–29 次恢复、75–152 个历史重演帧。

100 ms 门槛同时检查完整游戏回调的最大墙钟时间、画面提交间隔和新逻辑水位的停顿。各席均有至少一项超出门槛；通过该门槛本身也不代表持续 60 fps。完整回调统计保留了在窗口内开始、窗口外结束的调用，进度和画面间隔则在窗口末端截断，因此两个最大值的时间范围可能不同。

### 计时含义与长停顿

- **完整回调**覆盖实际 Emscripten 游戏 rAF 回调，包括没有 `onGameFrame` 通知的历史追赶。原生 `onGameFrame.ms` 单独保留，不能用它的子集统计替代全部回调。
- **新逻辑帧**按观察到的最大 `NextFrame` 水位计数；恢复后重新走过的帧不重复计算为新进度。
- **画面提交**计数游戏画布默认 DRAW framebuffer 的颜色 blit，表示提交完成；没有测量 GPU 完成时间或显示器扫描输出。
- 回调结束后的状态观察另行计时，修复后各席 P95 为 0.6–2.8 ms。生产外壳及回调内的轻量记录仍包含在完整回调的墙钟时间内。

双人 mode 2 的最长画面间隔约为 2.94 秒，其中一个完整游戏回调耗时 2,923.9 ms，原生通知报告 2,909.4 ms。该次长调用发生在该页约第 23.7–26.6 秒，早于该页 30 秒周期保存请求；该回调的逻辑水位从 322 推进至 323，恢复和历史重演计数均未增加。整条 2,940.7 ms 呈现间隔中，游戏回调覆盖 2,936.0 ms，额外 observer 覆盖 0.8 ms，其余 3.9 ms 尚未归因。它说明长停顿也发生在普通前推的原生游戏调用区间；本次没有采样 profiler，不能进一步把这段时间分配给模拟、绘制、驱动等待或系统调度。

双人 mode 0 还记录到一个 1,255.3 ms 的跨窗口结束回调，其中有一次恢复和一帧历史重演，且没有 `onGameFrame` 通知。它按规则计入完整回调最大值。紧接其后的额外状态观察耗时 395.3 ms，也如实单列；因此不能把这组观测视为无开销测量。两个席位的周期存档都发生在该场固定窗口之后，不能据此把该场的窗口内低帧率直接归因于保存。

代码中的“最多重演 4 帧 / 4 ms”是每次恢复驱动在完整帧执行后的软预算。一次浏览器回调可以调用多次恢复驱动，外层在完整调用之后检查 16.67 ms 的分批预算。**这些预算都不是单帧或浏览器回调的硬耗时上限。**

## 自动存档修复与真实持久化

首轮四个回滚场景的观察检查出现了 `Error`。一次独立诊断直接记录到：周期保存先成功导出确认 Replay，随后 `_th15_save_scores()` 因为仍有未确认预测状态返回 0；错误字符串为空，旧外壳把它抛成 fatal `Error`，并调用 `_th15_loop_pause(1)`。诊断保留了原生返回值、调用栈、状态和同页时间轴，单独标为诊断，不混入性能成绩。

修复使用带 token 的原生保存请求。等待期间继续处理网络和纠正，在下一次输入采样与前推前建立确认屏障；只有输入前缀已经 reconciled，且保留帧和 journal 均清空时，才执行真实 `app->save_settings()`。原生完成后解除模拟屏障，JS 再导出确认 Replay 并等待真实 `FS.syncfs` 完成。Host 的实时输入可以在 sync 等待期间获得处理，文件和生命周期操作保持顺序。超时、旧 world 的取消和真实失败都有明确结果。

新六场在固定性能窗口之后继续运行，覆盖自然发生的 30 秒自动保存，再让所有席位同时提交 Host sync 与右移射击。证据包括 native 完成、实际 FS 回调、输入 ACK 早于 sync ACK、确认 Replay 中的右移与射击，以及从真实 IndexedDB `FILE_DATA` 读出的 `scoreth15.dat` / `th15.cfg` 字节和原生文件验证结果。

首场新测试的原始 `saveValidationPassed` 为 false：新增校验器把 IDBFS 的 `Int8Array` 与 MEMFS 的 `Uint8Array` 直接按数值比较。两席分数文件各有 15,045 个这种表示差异。独立核对全部 30,149 字节后，实际字节差为零，双方 SHA-256 均为 `26764f694fda54b8b47ad9a1a84752ba31988ffe9a78779c41a6bdd3ec1bf75f`。原始 false 回执保持不变，另存 `independent-persistence-byte-audit.json`。校验器增加高位字节、非零 byteOffset 和真实错误字节的回归测试；其余五场的原始保存检查均通过。首场性能窗口没有重跑或替换。

原始保存回执的通过数因此是 **5/6**；首场的独立字节审计另外提供实际持久化一致的证据。这两个结果在机器摘要中分别记录。

## 复现入口

准备对应 DATA、共用字体、CP932、Emscripten 6.0.9 和 Chromium 后，先运行正式构建、打包和模块检查：

```bash
node launcher/scripts/build-runtime.mjs --game=th15 --variant=multiplayer \
  --emsdk="$EMSDK" --emscripten-version=6.0.9 --jobs=4
node ports/th15-mp/portable/package-eagler.mjs --multiplayer
node ports/th15-mp/portable/multiplayer/module-test.mjs --multiplayer-only
```

为 `TH15_TEST_ARCHIVE`、`TH15_TEST_FONT`、`TH15_TEST_UNICODE_FONT`、`EAGLER_CHROME_PATH`、`TH15_LAUNCHER_ROOT` 和 `EAGLER_RELAY_ROOT` 提供实际路径，冻结完整 Runtime 后运行：

```bash
node ports/th15-mp/portable/multiplayer/performance-browser.mjs \
  --mode=0 --players=2 --duration=15 \
  --runtime=/absolute/frozen-runtime --output=/absolute/new-results
```

选择 `--mode=0|1|2` 和 `--players=2|3`，每场使用新目录。runner 拒绝覆盖已有 `receipt.json`。结果分别提供 `observationPassed`、`saveValidationPassed` 和 `thresholdsMet`；性能门槛必须读取 `thresholdsMet`，不能根据进程退出码推断。
