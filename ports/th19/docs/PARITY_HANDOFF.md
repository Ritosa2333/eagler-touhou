从 Draft PR #214 拉取代码，在独立工作树继续。先集中跑通一场魔理沙镜像对局。采集源码、基线配置和对照样本见 [tools/parity](../tools/parity/)。

Windows Server 本地续接的魔理沙镜像验证见[2026-11-11 归档](../../../archive/th19-marisa-parity-20261111/README.md)。该记录保存具体构建、已比较帧范围、各字段首差和回滚结果。

额外五组种子各 36000 帧的长程结果与首差左右截图见[五种子验证记录](../../../archive/th19-marisa-multiseed-20261112/README.md)。

## 最终目标

用真实运行的 Windows 原版 th19 当参照，让新版 Web 在相同对局设置、种子、输入及模拟帧下复现原版行为和画面。目标是覆盖范围内的完整对局状态逐帧一致，画面在相同渲染条件下逐像素一致。先从 VS → CPU 的魔理沙镜像入手，跑通后再自动批跑所有机体和所有卡各一遍，无需排列组合。用现有回滚与录像路径做回归，画面同时检查菜单、轮次演出、实战和结算。

## 用户已授权的工作

- 可以直接反汇编、反编译和调试本地原版 th19.exe，可以读进程内存、跟踪调用，并在隔离副本上加观测钩子。使用新电脑本地安装的原版游戏，按下方 SHA-256 验证版本。原版文件和个人存档留在本机，实验写入测试副本和独立 AppData。
- 用户明确要求把此前手动填写的偏移都反编译核查。包括采集器的地址、结构字段和调用点，以及 Web 为了贴近原版手调的坐标、布局、动画时点和判定常量。沿原版调用链追到读写点、资产或脚本表，核对数值、单位、坐标系和更新阶段，并用实际运行采样交叉验证。每条记录对应的 exe 哈希、地址或模块 RVA、函数或脚本、原版证据和 Web 使用点。仍待验证的条目标清楚。
- 可在独立工作树修改新版并运行构建、测试、批量采集和对拍。先复用自己社区已有的 replay verifier、rollback、原版采集器和 Ju.N.Owen 驱动。优先走脚本、命名管道、进程观测和浏览器自动化，Computer Use 留给脚本暂时进不了的界面。GitHub 的标题、正文和评论先给项目维护者审阅。

## 工作流程

1. **先复现基线。** 校验原版版本，启动原版 VS CPU，记录左右机体、卡、难度、两路初始 RNG、规则、输入与原版采集版本。先用下文两组无卡 Lunatic 对局，确认原版重复跑出的开局状态一致，再让 Web 用相同设置和种子跑。用轮次段和逻辑帧对齐，先查第 113 帧命中和第 125–126 帧差异。
2. **用游戏状态验证。** Web 侧优先复用现有回滚快照的取数能力。原版侧按同一语义采集。参考仓库内的 Replay Verifier 和 th19 回滚测试，复用采集契约、逐帧比较、轨迹拼接和报告。参见 [Replay Verifier](../../../common/testkit/replay-verifier/README.md) 与 [回滚测试](../tests/rollback-session.test.mjs)。先比较双方位置、输入、生命、计时、两路 RNG、敌机、弹丸、命中和脚本进度，逐步补齐卡片、计分、轮次及结算。对象按稳定的生成顺序或可验证的对应关系匹配。缺帧、字段缺失和卡片未触发要单独标记。文件能读、能启动和总帧数相同只算流程检查。
3. **定位首个分叉。** 按轮次和模拟帧找第一个不同字段。对分叉前后几帧加窄采样，跟踪原版调用顺序、状态读写、RNG 取数和 ANM/ECL 脚本，必要时反编译到对应函数。保留原版与 Web 的同帧值、调用证据和截图。常量优先追到原版逻辑或资产，确认差异的原因后再改 Web。
4. **修完立即回归。** 改动集中在导致分叉的执行阶段。先跑原用例、交换双方的对局和相关旧录像，再跑回滚重演及现有构建和测试。比较修复前后的首个分叉和通过区间。发现下一处差异就记录并继续定位。碰撞时序试验与已验证提交分别保存。
5. **并行验证画面。** 在对应逻辑帧抓原版 D3D9 输出和 Web canvas。对齐分辨率、裁切、缩放和呈现阶段，再输出原版、Web 和绝对 RGB 差分，记录变动像素比例与范围。旧截图降采样可用于诊断，最终逐像素比较需同分辨率。画面按 HUD、层级、坐标、字体、混合、菜单和转场查。状态一致、画面仍有差异时沿渲染路径追查。
6. **批跑并及时交接。** 机体扫描固定难度、种子、无卡规则和基准对手，每场只换一台机体。卡片扫描固定双方机体及其他规则，每场只换一张卡，确认卡进入对局且已触发对应行为。遇到单侧特有分歧时再换边复跑。先扫开局，遇到分叉就存证并继续下一例。开局已对齐、要跑到后段时再尝试变速，并先核对变速前后相同逻辑帧。让采集工具后台跑，同时整理已有证据或检查下一处调用，持续维护覆盖清单供接手。

每例至少留下用例设置、原版和 Web 版本、已比较帧范围、首个状态差异、对应截图、重跑命令和当前状态。全程完成的判据是每台机体、每张卡都已覆盖且相关行为已触发，验证区间推进到完整对局，状态与画面均有同帧证据。阶段性成果按实际对齐区间汇报。

## 采集真正的原版

在 Windows 上使用本地安装的原版 th19。已验证的原版可执行文件 SHA-256 为 `804107d9033601f69c251a5e6e449bd88d9add36591129db394765295893bac6`。

基线对局为 Lunatic 灵梦对魔理沙和魔理沙对灵梦，均为 VS CPU、两命、无卡、600 秒。两路第 0 帧 RNG 为 3058262 和 424182232。先确认原版进程实际选中了对应模式、难度和机体。

原版采集用独立 AppData 和隔离副本，保留原版游戏逻辑。此前的 CPU 驱动基于 Ju.N.Owen 的 `534f26466c10a5ebab1fac222b1a410b6b053424`，通过命名管道提交对局配置，在对局初始化时设置第二路 RNG。可从现有社区驱动和仓库的 Windows 进程采集器接入。原版画面采样点为 D3D9 Present 前。采集 RNG 调用与第 122–130 帧碰撞数据时，给状态、调用和截图都附上轮次段和模拟帧号。参见 [th19 录像说明](REPLAY.md) 与 [Windows 进程采集器](../../../common/testkit/replay-verifier/windows-process-reader.py)。

从源码仓库根目录取工具和对局配置。用 Windows x86 Native Tools 命令行编译 D3D9 观测器。工作目录与原版资源需要在同一 NTFS 卷。Ju.N.Owen 补丁沿用上游 GPL-3.0，随附 [许可](../tools/parity/LICENSE.JuNOwen)。

~~~powershell
$tools = (Resolve-Path ports/th19/tools/parity).Path
$work = New-Item -ItemType Directory -Force "$env:TH19_PARITY_WORK"
git clone https://github.com/progre/junowen.git "$work/junowen"
git -C "$work/junowen" checkout --detach 534f26466c10a5ebab1fac222b1a410b6b053424
git -C "$work/junowen" apply "$tools/junowen-cpu.patch"
Push-Location "$work/junowen"
cargo build --release --locked -p th19replayplayer --target i686-pc-windows-msvc
Pop-Location
Push-Location $work
cl /nologo /O2 /EHsc /LD "$tools/observe-d3d9.cpp" /link /OUT:d3d9.dll
Pop-Location

$driver = "$work/junowen/target/i686-pc-windows-msvc/release/th19replayplayer_hook.dll"
$hash = (Get-FileHash $driver -Algorithm SHA256).Hash.ToLower()
foreach ($match in @('reimu-marisa', 'marisa-reimu')) {
    python "$tools/capture-native.py" --original "$env:TH19_ORIGINAL" `
        --observer "$work/d3d9.dll" --output-dir "$work/native" `
        --cpu-fixture "$tools/samples/cpu-lunatic-$match-no-cards.bin" `
        --cpu-driver $driver --cpu-driver-sha256 $hash --cpu-second-rng 424182232 --isolated-pipe --rng-calls --timeout 60
}
~~~

先设置 TH19_ORIGINAL 指向本机原版安装目录，TH19_PARITY_WORK 指向同卷的实验目录。两场顺序运行，每个进程用独立命名管道。每次运行打印采集目录。也可以直接用仓库提供的样本验证 Web 工具。

批跑开局时，固定魔理沙作为对手，逐个替换左侧机体。卡片单独跑，固定灵梦对魔理沙，仅替换左侧卡。每例采到第 180 帧即可进入下一例。原版启动卡住时可设 TH19_CPU_START_DELAY 后重跑。有完整解锁的本地成绩档时，可用 `--score-profile` 将其复制到隔离目录。批跑会跳过同版观测器和驱动下已采够帧的用例。`--case` 可单独重跑某个机体或卡片编号。

~~~powershell
node "$tools/scan-native.mjs" "$env:TH19_ORIGINAL" "$work/d3d9.dll" $driver "$work/characters" 180 --isolated-pipe
node "$tools/scan-native.mjs" "$env:TH19_ORIGINAL" "$work/d3d9.dll" $driver "$work/cards" 180 --cards --isolated-pipe
~~~

逐例采集后，将成功用例的采集目录传给 `check-web.mjs` 并加 `--opening-only`。脚本从原版记录读取机体、卡和规则，分别报告两路 RNG 的首处分叉。带 `--rng-calls` 的新原版采集还会记录双方移动后的坐标及输入位，报告分别列出采样覆盖和首处差异。原版同一游戏帧号可能有多条呈现记录，报告单列 RNG 在这些记录间变化的帧。常规逐帧比较使用每个帧号的第一条记录。卡的入场选择经过检查，触发效果仍需按卡的行为另外取证。追单一分叉时，两端都可传 `--trace-window FIRST LAST`。原版另加 `--rng-calls`，Web 可用 `--rollback-window FIRST LAST` 比较指定区间重演前后的状态与画面。

原版同时启用 `--rng-calls --bullet-positions`，Web 用 `--through FRAME` 逐帧比较双场活跃敌弹。原版在 D3D9 Present 前读取弹丸管理器的活动链表，入口由 `0x40e0fb` 确认，弹丸状态由 `0x4ee3e9` 的筛选条件确定。报告按场地、弹型和颜色比较坐标集合，重复坐标按实际颗数计算，并列出缺采样帧和首组差异。回滚终点有弹丸采样时，同时比较重演前后的坐标。激光及玩家射击使用各自的采样路径。

长程 CPU 状态采集加 `--fast-state`。隔离进程进入实战后跳过原版的实时等待，帧率无上限。状态仍逐帧采集，绘制流程仍运行，每 60 个逻辑帧向屏幕提交一次。本机魔理沙镜像实测约每秒 442 个逻辑帧，与原速对照至第 7200 帧，两路 RNG、时钟、标志、输入、双方坐标和敌弹坐标均一致。加 `--minimized` 可以最小化启动且不抢焦点。同速的窗口与最小化采集逐帧对照至第 12525 帧，以上字段一致，六张同帧画面的像素差异均在 FPS 计数器内。Web 端可连续推进逻辑帧，只在指定帧渲染。需要对照原版完整画面时使用普通速度。

## 魔理沙镜像

固定 Lunatic、两命、无卡、600 秒，初始 RNG 为 3058262 和 424182232。原版第一轮连续采集至第 36320 帧，第二轮采集至第 9174 帧时达到采集时限。带输入和坐标的加速样本用 `--opening-only --through FRAME` 对拍。最新长测复跑至第 15000 帧。双方输入和玩家坐标一致至第 12571 帧，主 RNG 一致至第 12578 帧，各场活跃敌弹数量一致至第 12580 帧。下一处差异为第 12572 帧左侧 CPU 输入，Web 为 25，原版为 89。副 RNG 首次在第 832 帧分叉，敌弹坐标仍有微小误差，画面尚未完全对齐。

双场活动敌弹采样从第 1 帧起。两场弹数在第 1 至 12487 帧逐帧一致。第 12488 帧原版右场有 48 颗活跃敌弹，Web 有 49 颗。坐标完全一致的区间包括第 1 至 1042 帧和第 4157 至 4367 帧。第 1043 帧右场弹型 12、颜色 6 的弹有一颗横坐标相差约 0.00000763 像素。

原版反击弹由 `0x51c058` 进入通用发射路径，在 `0x4f42b7` 求正弦和余弦，乘以速度后才将分量存为单精度。补齐该顺序后，第 318 帧的偏差消失。场中央按 `0x51bed1` 直接生成有符号角度扰动，修复了第 542 帧开始出现的横坐标偏差。原版 `0x51c676` 使用两侧共用的飞行管理器，`0x51c7aa` 把新登记项放到表头。Web 按全场登记逆序结算抵达，复现第 979 帧左场先于右场的取数顺序。两颗反击弹的初速度均逐位一致，第 1144 帧的弹数差异随之消失。

第 1078 帧，原版在 `0x4f5ec9` 以当前精灵的完整尺寸检查出界，按 14 像素宽回收右场弹型 12、颜色 6 的弹。新版将脚本弹接入此判定，并复用绘制时的精灵编号映射。

第 1844 帧左场纯灵抵达时，原版在 `0x50c012` 立即执行接收对象的 ECL 初始化。Web 曾在右场更新之后才执行初始化，把同帧的两组取数分给了不同对象。移到抵达阶段后，纯灵的加速和转向与原版一致。第 1873 帧 CPU 看到的纯灵坐标对齐为 (0.55, 68.50)，同帧切换目标并向右移动。

第 2073 帧，`0x545811` 先发出纯灵，`0x51be8e` 再为抵达的反击弹取角度。Web 将纯灵发射移到反击弹抵达之前，已经抵达的纯灵仍在反击弹之后初始化。右场反击弹在第 2149 帧进入光圈，擦弹奖励的两次取数与原版一致。

## 历史分歧和基线回归

- 旧基线在 Web 第 125 帧先命中，原版第 126 帧才命中。第 125 帧原版符弹中心约 (-98.34, 262.70)，与 Web (-98.33, 262.69) 接近。旧 Web 对比移动前敌人中心 (-117.81, 253.76)，原版对比移动后中心 (-116.17, 251.72)。原版 0x5089f4 调用 0x509030 更新敌人，0x508a03 再调用 0x509980 检查伤害。第 126 帧原版命中动画脚本 8 的指令 117 从 2057716148 继续取数。
- VS 追踪符在敌人移动后按圆形或旋转矩形判定。两个换边用例的两路 RNG 逐帧一致至第 139 帧，追踪符命中帧为 113、126、128。第 126 帧的弹丸坐标原版为 (-102.93, 257.14)，新版为 (-102.79, 257.28)。原版逐敌移动后立即查伤害，新版在整侧移动后集中判定。后续有多个对象同帧碰撞时，应继续核对遍历顺序。
- 第 140 帧新版提前执行灵梦的低速星弹命中回调。原版 `pl00.sht` 低速组的星弹用脚本 7，类型 0，命中回调 1。原版第 141 帧经回调表 `0x5a03d0` 第 1 项进入 `0x54da60`，五次显式取数都用主 RNG `0x5c6620`。新版第 140 帧从副 RNG 多取了六次，含五次显式取数和一次 ANM 取数。继续对拍星弹命中位置、动画时点及双方各自的 RNG 调用。
- 第一轮批跑中，8 台机体完成了原版与 Web 的开局对拍。机体 7 原先在第 86 帧分叉。原版初始化回调 16 的 `0x54b284` 和更新回调 10 的 `0x54b0f5`、`0x54b16a` 在出生帧从主 RNG 取数。对齐出生更新后，两路 RNG 匹配至第 117 帧。卡片 1–3 已完成开局对拍，首个 RNG 分叉分别为第 123、140、86 帧。
