# 神灵庙绘制开销与补帧放大试验

六面末段的回调耗时主要落在绘制，灵体特效层和 STD 背景是最大的两个热点。受控 CPU 限速下，当前逐逻辑帧完整绘制的补帧循环会放大掉帧。着色器预热覆盖缺口已确认，但本轮六面同场景测量中，补足预热带来的 GPU 计时差异较小。

这些结果定位了可复现的负载和放大机制；用户报告设备、浏览器和准确输入未知，尚不能将其认定为所有玩家 40/20 FPS 的唯一原因。性能实验未合入产品代码。

## 测量数据

- [汇总、方法和构建身份](measurements.json)：生产与诊断 WASM 的 SHA256、固定输入摘要、热点、核心状态一致性及帧循环对照。
- [六面逐窗口数据](stage6-windows.json)：6 组构建／分辨率组合，每 300 帧的 CPU、GPU 区间、绘制批次、内存、VM、核心状态和调度耗时。
- [真实帧循环数据](realtime-windows.json)：原速与 CPU 限速条件下，基线和着色器候选的呈现率、逻辑推进率及补帧分布。
- [补帧 ABBA 对照](cadence-abba.json)：基线、单步、单步、基线顺序的重复测量。

这些 JSON 为游戏端性能测量，不包含原版素材、Replay 文件、原版反编译内容或画面捕获。

## 测量方法

- 数据采自原 monorepo 的修复提交 `a842a9e649048199acc775923c02882a3da0f66d` 所含源码。迁入独立仓库时保留原构建和输入身份，供复核历史测量。
- Windows Chrome，ANGLE D3D11，确认使用 NVIDIA GeForce RTX 4060 Laptop GPU。
- 生产基线 WASM SHA256：`b779867d56d5f44fbe2197afee47c916f4d047b66ab599a108ea28993bd88205`。
- 固定启动种子 7319、Lunatic、固定横向移动与射击输入，分别测试 1 倍和 2 倍渲染。
- 先运行正常标题入口，断言签名动画 VM 已清理，再进入真实六面资源和生产场景。每 300 帧统计一次，推进至第 5100 帧、神子登场对话。
- 为覆盖整个时段，外部诊断构建在每个测量窗口前补足残机；窗口内保持生产模拟。此输入是可重复的性能夹具，不是原版玩家录像或完整通关认证。
- CPU 数据为同步帧泵及调度回调的墙钟时间；GPU 数据为 `EXT_disjoint_timer_query_webgl2` 的计时间隔，可能包含命令流间隙，不将两者简单相加。
- 正式帧循环另从第 4200 帧开始运行约 4 秒，记录实际呈现次数、逻辑步数和补帧分布。CDP 6 倍、12 倍 CPU 限速是受控条件，不对应某个具体手机或显卡。
- 所有源码覆盖、测试输入、构建及原始日志都在外部 `D:\Containers\th13-work\artifacts`，不修改共享 Renderer 或生产游戏逻辑。

## 六面末段热点

第 3600..5100 帧的 2 倍渲染诊断构建中，调度回调计时的约 82.7% 属于绘制。主要回调每逻辑帧平均耗时：

| 回调 | 毫秒 |
| --- | --- |
| 灵体特效，Draw16 / ANM layer6 | 0.532 |
| STD 背景，Draw2 | 0.296 |
| ANM 更新，Update34 | 0.125 |
| ANM layer16，Draw33 | 0.124 |
| 对局更新，Update20 | 0.065 |

这个时段的 300 帧窗口最高平均约 746 个 GPU 绘制批次/帧。灵体层存在数百个 `astral.anm` VM；脚本 7/8/9 与 19/20/21 组合中的子体使用不同混合模式，会打断相邻合批。优化需要维持透明混合顺序。

堆在全部窗口中保持 115,998,720 字节；末段前四个窗口纹理上传为零，登场对话窗口上传 91,136 字节；GPU 回读为零。这些数据不支持将本次末段负载解释为反复大纹理上传或持续扩堆。跨关累计是否存在问题尚未覆盖。

## 着色器预热对照

基线预热使用 `GreaterEqual`，TH13 实际默认比较条件为 `Always`；未命中时进入 generic 着色器。实验仅扩展预热键，不改变实际透明度条件。

| 第 3600..5100 帧，2 倍渲染 | 基线 | 补充预热 |
| --- | --- | --- |
| 同步帧泵平均 CPU 毫秒 | 1.542 | 1.567 |
| GPU 计时间隔平均毫秒 | 1.071 | 1.030 |
| generic 批次比例 | 100% | 0% |

测量差异不支持将预热缺口单独认定为本轮六面瓶颈。1 倍/2 倍的此机器对照，也未出现四倍像素量对应四倍帧耗时的现象。

两种分辨率各比较第 600、3900、4200、4500、4800、5100 帧，共 12 对最终画布，逐像素一致；各窗口回放核心状态、随机数状态及 VM 数量一致。这是实验前后的一致性检查，不是独立原版 GPU 认证。

## 补帧机制的因果对照

`BrowserRuntime.cpp` 的 `drive_one_frame` 对欠下的逻辑步逐个调用 `sample_and_tick`；每次经 `ApplicationState::step` 进入完整 `display->draw()`，最后才统一 `commit()` 呈现。一次回调最多推进四步，因此慢设备会在一次呈现前重复执行多次完整绘制。

固定六面第 4200 帧，2 倍渲染，按基线、单步上限、单步上限、基线顺序重复测量：

| 受控 CPU 条件 | 基线显示 FPS | 诊断单步上限显示 FPS |
| --- | --- | --- |
| 6 倍限速 | 23.3、46.9 | 54.2、54.9 |
| 12 倍限速 | 4.6、4.3 | 15.5、15.6 |

12 倍限速的基线主要以四步回调运行，一次采样中 65 次完整绘制只对应 17 次呈现。原循环显示与逻辑推进速度发生明显分离，支持“负载超过预算后，补帧绘制继续增加负担”的判断。6 倍条件波动较大，不据此给出固定加速比。

单步候选使用 `min(1, cadence.advance(delta))`，丢弃了已经被时钟扣除的欠帧工作，会改变逻辑时间推进；它仅用来隔离放大机制，不能发布为最终修复。正式方案需要同时验证模拟速度、输入、随机数、画面反馈和音频时序。

## 开局与结论范围

正常菜单路径的一面首次进入抽样出现约 10.2 MiB 纹理上传、WASM 堆从约 76.8 MiB 增至 110.6 MiB，以及一次约 62 ms 的同步调用峰值。该耗时来自无头软件渲染环境，能说明首次装载工作集中，不能外推为用户设备的卡顿时长。

本机无 CPU 限速的真实循环约 59.7 FPS，未复现用户原设备的持续 40/20 FPS。因此当前结论是：已定位六面绘制热点和可复现的补帧放大机制；开局首载峰值、预热覆盖缺口分别有证据，用户报告的端到端原因仍需出现问题的设备数据。

后续优先减少保持顺序的绘制提交开销，并设计保留原版时序的补帧策略；结合正式网站可选诊断数据验证各类设备。全游戏独立原版 GPU 认证保持 BLOCKED。
